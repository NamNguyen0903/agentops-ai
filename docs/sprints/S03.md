## Persistence decisions and limitations

- `app.research_tasks`: UUID primary key and `owner_id` FK to `app.users`.
- Six unchanged PRD states: queued, running, completed, insufficient_evidence,
  failed, timed_out. Submission writes queued only, with null stage/error/start/end.
- DB checks reject invalid state, blank question/key, non-object scope, wrong
  fingerprint length, inconsistent timestamp shape/order and free-form error text.
  Error category is a bounded machine-code shape; future writers must use an
  allowlisted category, never provider/exception text. No transition engine exists.
- `created_at`/`updated_at` default to transaction time. Future lifecycle writers
  must maintain `updated_at`, terminal immutability and publication barriers.
- Input scope has optional geography/category/time_scope text and competitors
  as a string collection. These are descriptive intent, not executable filters.
  Unknown keys and coercions are rejected. JSON arrays normalize to immutable tuples
  for validation and back to arrays in JSONB. Question text is not case-folded or
  silently trimmed. NUL is rejected before PostgreSQL.
- Initial configurable validation hypotheses: question 4,000 characters and scope
  2,000 characters in its default-expanded JSON representation. WP02 must supply
  the same configured limits to validation and submission. This is an internal
  persistence input contract, not an already-approved public endpoint schema.
- Required nonblank idempotency key: at most 128 characters, scoped to owner.
  SHA-256 fingerprint covers version 1 canonical JSON of question and normalized
  scope. Semantically different text/list order counts as different input.
- Unique `(owner_id, idempotency_key)` plus PostgreSQL INSERT ON CONFLICT and a
  subsequent SELECT under READ COMMITTED implements create-or-reuse. Caller must
  open and commit the transaction; the repository never commits or retries it.
  API must not return HTTP 202 until commit succeeds. Conflict errors contain no input.
- Deleted rows remain reserved for idempotency; replay fails instead of reviving
  a task. Detail/history hide deleted rows. Hard deletion and key retention are
  not implemented and require later policy decisions.
- Composite retry-parent FK enforces same owner; self-parent is rejected. User
  deletion and parent deletion use RESTRICT, avoiding unauthorized cascading
  research deletion. Future purge needs an explicit dependency order/policy.
- Owner/history and partial queued indexes support reads and future eligibility
  scans. History uses descending `(created_at, id)` keyset order. No worker claim,
  admission serialization or exactly-once execution guarantee is implied.
- Owner filters are application-level; no RLS is added. Repository owner UUIDs
  must come from the authenticated server principal in WP02, not request bodies.
- The runtime role gets explicit research DML only. Schema/Alembic privileges stay
  restricted; migrations still reject anything except the disposable test target.
  PostgreSQL tests connect as migrator, while lifecycle assertions verify app-role
  grants. This does not prove a deployed app-role login or production migration.

ADR-0003 was absent in the inspected tree. No material worker/lease/recovery
decision is needed for the explicitly requested persistence foundation. No ADR is
created or accepted here. Stop affected future work if it requires those decisions.
